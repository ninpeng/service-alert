# 장애 이력 검색 설계

## 목적

Service Alert의 주 화면은 현재 장애와 수집 상태를 한눈에 확인하는 대시보드다. 장애 이력 검색은 과거 기록이 필요할 때만 사용하는 보조 기능으로 추가한다. 메인 대시보드의 정보 밀도와 첫 화면 구성은 유지하고, 별도 `/incidents` 페이지에서 전체 이력을 조회한다.

## 목표

- 서비스별 전체 장애 이력을 별도 화면에서 조회한다.
- 제목, 서비스명, provider로 검색한다.
- 상태, 영향도, 기간, 기록 유형을 필터링한다.
- 진행 중 장애와 해결된 장애를 구분한다.
- 검색 조건을 URL에 유지해 새로고침, 뒤로 가기, 링크 공유가 가능하게 한다.
- 원문 링크와 마지막 수집 시각을 결과에서 바로 확인한다.
- 서버 조회와 페이지네이션으로 데이터가 늘어나도 대시보드 응답 크기에 영향을 주지 않는다.

## 비목표

- 메인 대시보드를 검색 중심 화면으로 바꾸지 않는다.
- 서비스 활성화, Slack 설정 변경, 수동 worker 실행 같은 쓰기 기능을 추가하지 않는다.
- 인증, localhost 바인딩, 외부 접근 제어를 이번 범위에 포함하지 않는다.
- CSV/JSON 내보내기, 저장된 검색 조건, 다중 컬럼 정렬을 추가하지 않는다.
- TanStack Table, React Query, Zod 같은 새 의존성을 추가하지 않는다.
- 데이터베이스 스키마나 인덱스를 변경하지 않는다.

## 사용자 흐름

1. 사용자는 메인 대시보드에서 현재 상태를 확인한다.
2. 과거 장애가 필요하면 사이드바의 `장애 이력` 또는 `최근 장애`의 `전체 이력` 링크를 선택한다.
3. `/incidents`는 최근 30일의 실제 장애를 최신순으로 보여준다.
4. 사용자는 검색어와 필터를 조정하고 `조회`를 선택한다.
5. 결과에서 상태, 영향도, 발생·해결 시각, 마지막 수집 시각을 비교한다.
6. 필요한 사건은 원문 링크로 공식 상태 페이지를 연다.
7. `대시보드` 링크로 현재 상태 화면에 돌아간다.

## 정보 구조

### 메인 대시보드

- 현재 운영 상태, 서비스 상태, 최근 장애, worker 결과, Slack 이력을 그대로 유지한다.
- 사이드바 `장애 이력` 링크를 `/incidents`로 변경한다.
- `최근 장애` 헤더에 작은 `전체 이력` 링크를 추가한다.
- 대시보드가 전체 장애 목록을 추가로 조회하지 않도록 기존 서비스별 6건 제한을 유지한다.

### 장애 이력 페이지

- 기존 사이드바와 시각 체계를 재사용한다.
- 페이지 제목은 `장애 이력`, 보조 문구는 검색 결과의 용도를 짧게 설명한다.
- 상단에는 조밀한 검색·필터 영역을 둔다.
- 본문에는 전체 건수, 결과 테이블, 페이지 이동을 순서대로 둔다.
- 대시보드보다 부차적인 화면이므로 요약 카드나 별도 운영 지표는 추가하지 않는다.

## URL 계약

모든 조건은 `/incidents`의 query string으로 표현한다.

| 파라미터 | 허용 값 | 기본값 | 동작 |
| --- | --- | --- | --- |
| `q` | 최대 100자의 문자열 | 빈 문자열 | 앞뒤 공백을 제거하고 incident 제목, 서비스명, provider를 대소문자 구분 없이 검색 |
| `service` | provider 식별자 또는 `all` | `all` | 특정 서비스만 조회 |
| `state` | `all`, `active`, `resolved` | `all` | 진행 상태 필터 |
| `impact` | `all`, `critical`, `major`, `minor`, `none`, `unknown` | `all` | 정규화된 영향도 필터 |
| `period` | `24h`, `7d`, `30d`, `all` | `30d` | 사건 활동 시각 기준 기간 필터 |
| `type` | `incident`, `maintenance`, `all` | `incident` | 실제 장애와 예정 점검 구분 |
| `page` | 1 이상의 정수 | `1` | 25건 단위 페이지 |

허용되지 않은 값은 오류로 중단하지 않고 기본값으로 정규화한다. 필터 폼은 `page`를 제출하지 않아 조건 변경 시 항상 1페이지에서 시작한다. 요청한 페이지가 전체 페이지 수보다 크면 마지막 유효 페이지로 canonical redirect한다. 결과가 없으면 1페이지를 유지한다.

## 상태와 시각 판정

### 활동 시각

기간 판정은 `updatedAt`, `startedAt`, `firstSeenAt` 순서의 첫 유효 값을 사용한다. Prisma 조건은 같은 의미가 되도록 nullable 필드를 명시적으로 조합한다. 결과 정렬은 `updatedAt DESC`, `startedAt DESC`, `firstSeenAt DESC`, `id DESC` 순서로 고정한다.

### 진행 상태

종료 상태 집합은 정규화된 `resolved`, `complete`, `completed`, `postmortem`이다.

- `resolved`: `resolvedAt`이 있거나 `status`가 종료 상태 집합에 포함된다.
- `active`: `resolvedAt`이 없고 `status`가 종료 상태 집합에 포함되지 않는다.
- `all`: 진행 상태 조건을 추가하지 않는다.

provider별 상태 문자열 차이를 한 곳에서 관리하도록 상태 판정과 Prisma 조건 생성을 별도 순수 함수로 분리한다. 예정 점검 포함 여부는 진행 상태와 독립적으로 `isMaintenance`로 판정한다.

### 영향도

- `critical`, `major`, `minor`, `none`은 저장된 소문자 값과 일치시킨다.
- `unknown`은 `impact`가 `null`이거나 빈 문자열인 기록을 의미한다.
- `all`은 영향도 조건을 추가하지 않는다.

## 서버 구조

### 검색 파라미터 모듈

검색 파라미터 파싱, 기본값, 기간 시작 시각, 페이지 offset, URL 재구성을 담당하는 순수 모듈을 둔다. 페이지 컴포넌트와 UI 컴포넌트는 원시 query string을 직접 해석하지 않는다.

### 조회 모듈

정규화된 검색 조건을 Prisma `where`와 `orderBy`로 변환한다. 다음 조회는 가능한 한 병렬로 실행한다.

- 필터 선택지에 사용할 서비스 목록
- 조건에 맞는 전체 incident 수
- 현재 페이지의 incident 25건과 연결된 서비스

반환값에는 정규화된 조건, 전체 건수, 전체 페이지 수, 결과 행, 서비스 선택지를 포함한다. 별도 JSON API를 만들지 않고 서버 페이지가 조회 모듈을 직접 호출한다.

### 공유 셸

현재 `page.tsx`에 포함된 사이드바를 작은 서버 컴포넌트로 추출해 대시보드와 장애 이력 페이지가 공유한다. 페이지별 본문과 상단 제목은 분리한다. 이번 기능에 필요하지 않은 대시보드 컴포넌트 리팩터링은 하지 않는다.

## 화면 구성

### 필터 영역

- 검색 입력: 제목, 서비스명, provider 검색
- 서비스 select
- 상태 segmented control: 전체, 진행 중, 해결됨
- 영향도 select
- 기간 select: 24시간, 7일, 30일, 전체
- 유형 select: 장애, 예정 점검, 전체
- `조회` 버튼
- 기본 URL `/incidents`로 이동하는 `초기화` 링크

폼은 native GET 제출을 사용한다. 상태 segmented control은 다른 query parameter를 보존하고 `page`만 제거하는 링크로 구현한다. 필터 폼에는 현재 `state`를 hidden 값으로 포함해 다른 조건을 제출해도 선택한 상태가 유지되게 한다. 키보드 포커스와 현재 선택 상태를 명확히 표시한다.

### 결과 영역

데스크톱에서는 다음 열을 갖는 실제 HTML table을 사용한다.

- 서비스
- 장애 제목
- 상태 / 영향도
- 발생 시각 / 해결 시각
- 마지막 수집
- 원문 링크

한 행 전체를 중첩 링크로 만들지 않는다. 원문 링크는 외부 링크 아이콘과 함께 새 탭으로 연다. 긴 제목은 줄바꿈하고 시간 값이 없으면 `기록 없음`을 표시한다.

모바일에서는 열을 숨기지 않고 각 행을 세로로 재배치한다. 서비스, 제목, 상태가 먼저 보이고 시간과 원문 링크가 뒤따른다. 텍스트와 컨트롤이 컨테이너를 넘거나 겹치지 않아야 한다.

### 페이지 이동과 빈 상태

- 결과 상단에 `총 N건`과 현재 조건의 기간을 표시한다.
- 하단에 이전, `현재 / 전체 페이지`, 다음 컨트롤을 둔다.
- 첫 페이지의 이전과 마지막 페이지의 다음은 비활성화한다.
- 페이지 링크는 현재 검색 조건을 모두 보존한다.
- 결과가 없으면 `조건에 맞는 장애 이력이 없습니다`와 초기화 링크를 표시한다.

## 오류 처리

- 잘못된 query parameter는 기본값으로 복구한다.
- DB 조회 실패는 `/incidents/error.tsx` 경계에서 간결한 메시지와 재시도 버튼을 제공한다.
- 외부 원문 URL이 없으면 서비스 endpoint를 사용하고, 둘 다 없으면 링크 대신 `원문 없음`을 표시한다.
- 검색 입력은 Prisma parameter binding을 사용하며 SQL 문자열을 직접 조합하지 않는다.
- API나 mutation을 추가하지 않으므로 현재 읽기 전용 보안 경계는 바뀌지 않는다.

## 성능

- 페이지당 25건만 서버에서 직렬화한다.
- 전체 건수와 결과 목록은 독립 query로 병렬 실행한다.
- 메인 대시보드 조회량은 늘리지 않는다.
- 현재 SQLite 규모에서는 기존 인덱스로 시작한다.
- 데이터 증가 후 실제 측정에서 병목이 확인되면 활동 시각 인덱스나 전문 검색을 별도 작업으로 검토한다.

## 테스트 전략

### 단위 테스트

- 기본 query가 최근 30일, 실제 장애, 1페이지로 정규화되는지 확인한다.
- 허용되지 않은 값, 음수 페이지, 긴 검색어가 안전하게 정규화되는지 확인한다.
- 기간 시작 시각과 pagination offset을 확인한다.
- 진행 중, 해결됨, 예정 점검, 영향도 조건의 Prisma 필터를 확인한다.
- 검색어가 제목, 서비스명, provider 조건으로 변환되는지 확인한다.
- 현재 조건을 보존하는 상태·페이지 URL 생성을 확인한다.
- 종료 상태 집합과 nullable 영향도 판정을 확인한다.

### 회귀 검증

- 기존 대시보드 테스트와 worker/provider 테스트를 모두 실행한다.
- TypeScript, ESLint, production build를 실행한다.
- 새 페이지가 기존 대시보드 조회 결과나 worker 동작을 변경하지 않는지 확인한다.

### 브라우저 검증

- 흐름: 대시보드 로드 → `전체 이력` 선택 → 기본 30일 결과 확인 → 서비스와 상태 필터 적용 → URL 및 결과 변경 확인 → 초기화 → 페이지 이동.
- 데스크톱과 모바일 viewport에서 빈 화면, Next.js 오류 overlay, 겹침, 잘림, 가로 스크롤을 확인한다.
- 브라우저 console의 관련 error와 warning이 없는지 확인한다.
- 결과 없음 상태와 외부 원문 링크를 확인한다.

## 완료 기준

- 대시보드는 현재 상태를 한눈에 보는 주 화면으로 유지된다.
- `/incidents`가 최근 30일의 실제 장애를 기본으로 보여준다.
- 모든 승인된 필터가 URL과 Prisma 조회에 반영된다.
- 페이지네이션이 25건 단위로 검색 조건을 보존한다.
- 원문과 마지막 수집 시각을 각 결과에서 확인할 수 있다.
- 새 의존성과 DB schema 변경이 없다.
- 자동 테스트, 타입 검사, 린트, production build, 브라우저 검증이 통과한다.
